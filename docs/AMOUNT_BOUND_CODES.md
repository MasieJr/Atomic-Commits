# Amount-bound payment codes: proposed architecture and security model

This is a design proposal, not an implemented payment method. It adds an online-issued bearer credential with a lifetime of at most 30 minutes. It does not extend the lifetime of an offline TOTP code, create spending authority, or prove that a payment settled. The payer needs a usable, previously approved provider grant. The merchant and backend must be online at redemption.

## Checkout and currency choices

1. The merchant tells the payer the exact amount and currency to receive. The payer connects to the service, selects a verified payer wallet and active grant, and enters or confirms the merchant's amount and currency. The service also shows the maximum debit in the payer wallet's asset, including conversion costs. The payer explicitly confirms both values and the selected grant before issuance.
2. The server issues a single-use code and displays its expiry. The payer presents the code as a QR or a long copyable string. The code contains no provider credential. It is a bearer credential: anyone who obtains it may try to redeem it first. A merchant binding, when available and confirmed at issuance, reduces that risk. An unbound code can be redeemed by any eligible merchant for the exact authorized receive amount, so the UI must say so.
3. The authenticated merchant submits the code, the exact receive amount and currency, the selected verified receiving wallet, and an idempotency key. The server claims the code and reserves the maximum payer debit before requesting a fresh provider quote. A code for a different amount, currency, scale, or bound merchant is rejected.
4. If the quote matches the authorized receive amount and the debit does not exceed the authorized maximum, the server may submit once. The merchant sees pending until provider evidence confirms settlement. Expiry of the code after a valid claim does not imply that an in-flight payment failed.

The amount bound to the code is the **merchant receive amount**, not an ambiguous number of payer units. Store every amount as a positive canonical integer minor-unit string plus asset code and scale, using exact integer arithmetic. For example, a code for EUR scale 2 and `1000` authorizes exactly EUR 10.00 received, not ZAR 10.00 or EUR 1,000. It also binds a maximum payer debit with its own asset and scale. When both wallets use the same asset, the maximum still covers fees; it is not assumed equal to the receive amount.

When currencies differ, the server obtains a fresh quote for the exact receiver amount. It verifies the receiver wallet and receive amount, payer wallet and debit asset, quote validity, and a positive debit no greater than the payer-confirmed maximum, reservation, per-payment limit, and available grant budget. For example, EUR 10.00 received with a ZAR 200.00 maximum permits a quote debiting ZAR 195.00, but not ZAR 201.00. A changed rate, fee, unavailable conversion, expired quote, or mismatched amount causes rejection rather than a larger debit. The payer must issue a new code after reviewing a new maximum. Do not infer an exchange rate or round with floating-point arithmetic. Any replacement quote must pass the same checks and never widen the reservation.

## Credential and authority

Generate at least 128 bits of independent cryptographically secure randomness per code. Use a versioned, unambiguous encoding with a distinct `amount-bound-v1` credential type. A short six-digit code cannot provide this entropy and is not an acceptable substitute. QR or long manual entry is a deliberate usability trade-off. The service stores a keyed, domain-separated lookup digest, not the raw code. Keep the lookup key separate from the database and support key rotation without accepting expired records. Never put codes in URLs, analytics, crash reports, logs, traces, or notifications. Protect transport with TLS and prevent caching or screen capture where practical.

The server-side issuance record binds the digest to the authenticated payer, verified payer wallet, specific grant and grant version, issuing device or session and its revocation version, exact merchant receive money, payer maximum debit money, optional authenticated merchant scope, issue time, and expiry. A code is not a provider grant and must not carry provider tokens, continuations, or device secrets. Server time determines validity: `issuedAt <= now < expiresAt`, and `expiresAt` is no later than 30 minutes after issuance or any earlier known grant, device, or policy deadline. Unknown grant validity is not permission to assume 30 minutes of authority. The server must refuse issuance or redemption when the required authority cannot be established.

Issuance requires an authenticated payer, explicit confirmation of the bound values, a verified wallet, and an active eligible grant. The server validates requested fields and enforces per-user and per-device limits on outstanding codes. Code issuance does not reserve money. Other spending can exhaust the grant before redemption, so issuance is not a promise that funds remain available.

## Claim, reservation, and submission

The following are required implementation invariants, not claims about existing code:

- Authenticate the merchant and resolve a current verified destination on the server. Compare all supplied money fields exactly with the issuance record and check any merchant binding. A mismatch never changes the authorized amount or claims another code.
- In one durable transaction shared by all replicas, lock the relevant grant and credential records in a consistent order. Recheck server time, code state, payer, wallet, device, grant versions, revocation, merchant eligibility, and destination. Atomically create one attempt, permanently claim the credential, and reserve the full authorized maximum debit. A unique constraint prevents two attempts from claiming the same credential. No process-local lock is sufficient.
- Under the same grant budget lock, count confirmed spend and every active or unknown reservation, across **all** credential types sharing that grant. The sum plus the new reservation must not exceed the grant cap or other applicable budget. Check the maximum against the per-payment cap. If shared accounting or provider spending cannot be reconciled conservatively, refuse. A full maximum reservation can block concurrent purchases even if the eventual quote is smaller.
- After a validated quote, the hold may shrink to the exact quoted debit only if every later submit uses that quote or an equally constrained revalidated quote. Persist the quote, destination snapshot, and attempt before proceeding. Recheck relevant authority, revocation, quote validity, and grant state immediately before committing the transition to submission.
- The transaction that commits the submission transition is the local ordering point against cancellation. The worker performs at most one external submit for that attempt. No retry of an ambiguous external submission is allowed under the current provider contract. A crash after the transition but before or during the call is unknown, even if the call might never have left the process.

If the claim transaction's response is lost, query the durable attempt using its idempotency identity. Do not start a new payment until the result is known. After a definitive pre-submit failure or proven no-debit result, release the reservation, but retain the consumed credential and its replay record. A new checkout needs a new code. Retain records for the full validity and recovery window, plus the applicable audit retention period.

## Retries, settlement, and cancellation

Scope a merchant idempotency key to the authenticated merchant. Store a fingerprint covering the credential's keyed identity, credential version, exact receive money, destination, and merchant. A retry with the same key and fingerprint returns the same attempt and current status, even after code expiry. A different request under that key conflicts. A different key cannot claim an already consumed code. Concurrent requests must converge on one durable attempt. Use keyed fingerprints where secret-derived material is included, not raw codes in stored request bodies or logs.

Persist `SUBMITTING` before the external call. A timeout, malformed response, crash, ambiguous provider error, or missing outgoing identifier becomes `UNKNOWN` and keeps the reservation. Read-only reconciliation may locate and inspect the original outgoing payment; it must not submit a second debit. A missing entry in a listing is not proof of non-payment. Keep unknown holds across expiry, logout, device changes, and restarts. Release them only on authoritative proof of no debit, or commit them on verified success. An unresolved case needs operational escalation and may remain held indefinitely; a manual release requires independently documented provider evidence, not elapsed time alone.

Success requires provider evidence tied to the saved payer wallet, outgoing ID, quote, incoming ID, and destination, with the expected payer debit and exact merchant receive amount. Store the checked evidence and paid amounts with the attempt before showing a receipt. The current Test Wallet adapter checks outgoing and incoming resources and requires the sent and received amounts to match. An accepted submission, a quote, a claim, or a provider reference alone is not settlement proof. Partial, inconsistent, or unavailable evidence remains pending or unknown rather than success or a safe failure.

The payer may revoke an unused code. Cancellation and claim must serialize on the same credential record: if cancellation commits first, claim fails; if claim commits first, the code is consumed and cancellation must report the existing attempt rather than claim that payment was stopped. Before the submission transition, cancellation can prevent submission through a conditional state change under the same locks. Once submission is committed or may have started, cancellation cannot promise to stop a provider debit. Report pending and reconcile. Grant revocation must block future claims and submission transitions, but provider cancellation can race with an already committed or in-flight call. Provider cancellation failure or uncertainty is not proof that authority was revoked externally.

## Device, account, and abuse controls

On device loss, enrollment removal, session compromise, account closure, payer wallet unlinking, or grant replacement, revoke affected unused codes and increment the relevant server-side version. Recheck ownership and versions at claim and before submission. A new device or grant needs a newly issued code; never silently transfer one. Preserve attempts, holds, and read-only reconciliation access for payments already in flight, even when spending authority is revoked. A merchant wallet change must not redirect a claimed payment: bind and persist the verified destination at claim, reject a stale checkout selection, and use the snapshot for reconciliation.

Rate-limit issuance and redemption by authenticated account and device, merchant, network source, and globally, with stricter controls for failures and bursts. Bound outstanding active codes and request sizes, alert on distributed guessing or enumeration, and use generic invalid-code responses. Limits must work across replicas and fail closed if their shared enforcement is unavailable. Do not disclose whether a payer, code, grant, or device exists. These controls reduce guessing and abuse but do not prevent theft of a valid bearer code. Use independent non-secret attempt identifiers for support and sanitized, access-controlled audit events. Never log raw codes, request bodies containing codes, provider tokens, authorization headers, continuations, device secrets, or unfiltered provider errors.

## Existing offline behavior and compatibility

`backend/src/services/offline-redemption.ts` handles `totp-v1` using an enrolled device prefix and six decimal digits. Its default accepts the current 30-second step and one adjacent step on each side, with a device-and-step claim and a ten-minute keyed recent-code replay guard. It obtains the receive amount from the merchant rather than binding it in the TOTP. The existing signed-instruction domain path in `backend/src/domain/payment-engine/offline-redemption.ts` has separate signed ceiling and exact-purchase forms. See [offline spending and signed QR](offline-spending-and-signed-qr.md) for their scope and development evidence.

The new credential must have explicit versioned parsing and separate issuance, lookup, and replay records. Never interpret an old TOTP as a 30-minute code, reuse its secret, expand its acceptance window, or fall back from a failed new code to TOTP. Preserve current offline generation and redemption semantics for existing clients. Payer offline use remains the existing TOTP or signed-instruction experience, not this online issuance flow. Both paths need a common durable grant budget and reservation transaction before the new method can safely share a grant with them. The current TOTP service releases claim state on a definitive no-debit outcome; the new credential's permanently consumed rule is intentionally different and requires its own enforcement.

## Evidence, dependencies, and open decisions

The repository's `RedemptionProvider` contract supplies quote preparation, a single submit call, read-only outcome checks, lookup by quote, authority rotation, and grant cancellation. Its `PreparedQuote` expiry is optional. The Test Wallet adapter validates quote participants and exact receive amount, submits without an internal retry, and verifies outgoing and incoming resources on success. It scans a bounded outgoing listing for recovery. These are code contracts, not proof that every provider offers complete listings, reliable finality, enforceable quote lifetime, atomic cancellation, or definitive no-debit responses. Provider rejection classification also needs provider-specific evidence before treating an error as proof that no debit occurred.

The existing offline documentation records limited live Test Wallet development proofs, including conversion, but not production durability or real-money guarantees. Existing provider grants and token rotation do not establish a 30-minute grant lifetime or monthly reset. A local 30-minute credential cannot extend either. External spending, revocation, or provider state may change after a local check; provider-side limits and evidence remain necessary. Local atomicity alone cannot guarantee exactly-once external settlement.

Before enabling the feature, establish durable cross-replica claim and shared-budget enforcement, recovery and audit retention, secure device and key handling, and a provider-specific basis for quote expiry, debit bounds including fees, failure finality, settlement reads, and recovery after an unknown submit. If a provider cannot establish a required property, refuse that payment or keep it unresolved. Product and security review must settle merchant binding defaults, maximum-debit confirmation UX, issuance caps, rate thresholds, retention periods, and operational handling of indefinite holds. No provider interaction or implementation is implied by this document.
