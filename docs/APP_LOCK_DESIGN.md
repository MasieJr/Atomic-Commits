# App lock design

## Decision and security boundary

Offer an opt-in local app lock on the native Android Flutter app when the device supports biometric authentication or a device credential. Start locked after process launch, hide sensitive content when the app loses focus, and require unlock after the inactivity policy expires. The lock protects against casual access to an unattended app. It is not a backend authentication factor, proof of the account owner's identity, or protection against a compromised device or modified client. Anyone enrolled on the device may satisfy its local authentication policy.

The backend must continue to authenticate and authorize every protected operation, enforce grant and payment rules, and reject expired or revoked credentials. A successful local prompt does not renew a server session. The lock does not cancel an already submitted payment or revoke an offline device.

## Current project

- `mobile/pubspec.yaml` includes `flutter_secure_storage`, but not `local_auth`. The project has a native Android host and a Flutter web entry point in `mobile/web/`. No WebView host integration is established by those files.
- Android's `MainActivity.kt` extends `FlutterActivity`. `AndroidManifest.xml` declares internet access, not `USE_BIOMETRIC`. `mobile/android/app/build.gradle.kts` inherits the Flutter minimum SDK and uses a placeholder application ID and debug signing for release. Confirm the resolved SDK and release identity before shipping.
- `TokenStorage` persists the bearer token and user together. `ApiClient` installs the bearer token in a Dio header. `AuthController.initialize()` restores a session and retains the stored token on network errors. Local lock state must remain separate from that session state.
- `OfflineProfileStore` stores a TOTP secret in secure storage. `WalletCache` stores a read-only snapshot scoped by API origin and user. These are different from server authorization, and an offline profile cannot learn of remote revocation while disconnected.
- The current working tree contains ongoing changes. These observations describe the inspected files, not a claim that those changes are already released.

## Native Android approach

In a future implementation, add Flutter's [`local_auth`](https://pub.dev/packages/local_auth) and check compatibility with the project's Flutter SDK and Android minimum SDK. Its documented Android support starts at API 24. Follow the [Android plugin setup](https://pub.dev/packages/local_auth_android#setup): change the custom activity to `FlutterFragmentActivity`, declare `USE_BIOMETRIC`, and use the required AppCompat launch theme, including the night resource. Verify the resulting merged manifest and theme on supported Android versions.

Use `isDeviceSupported()` for device-level authentication. `canCheckBiometrics` reports hardware capability, not enrollment. `getAvailableBiometrics()` reports enrolled biometrics, but an empty list does not rule out a PIN, pattern, or password. Call `authenticate` with device-credential fallback allowed rather than `biometricOnly: true`. The system selects the available method; do not claim that a successful result proves a fingerprint or a specific person.

Offer enrollment only after account sign-in and a successful local prompt. Keep the app locked on cancellation, failure, lockout, missing enrollment, or platform errors. Explain the problem and let the user retry, set a device screen lock in system settings, or sign out. If local authentication is unavailable, do not advertise a biometric lock or silently mark the app unlocked. Require online account sign-in as the fallback, without claiming it protects locally retained offline secrets. Recovery after a changed or removed device credential must not bypass protected data: sign out and clear local secrets, or use a separately designed account recovery and re-enrollment flow.

The prompt result alone is an application-level gate. For stronger at-rest protection, investigate Android Keystore keys whose use requires device authentication, including key invalidation, backup and restore behavior, and recovery. Confirm the exact authenticator policy supported by each target Android version. `flutter_secure_storage` use in this repository does not establish that reads are bound to the prompt. Do not claim hardware-backed or per-use authentication without implementing and verifying it.

## Lifecycle and inactivity

Place a lock controller above authenticated routes and sensitive overlays, including deep links, payment codes, dialogs, and restoration. Initialize it locked before restoring sensitive UI. Maintain distinct signed-out, locked, prompting, and unlocked states. A successful prompt unlocks only the current account and current lock generation. Serialize prompts and discard late results after logout, account change, a new lock, or a real background transition.

On loss of focus, immediately cover sensitive content and disable input. `inactive` can also occur for a system authentication dialog, so do not treat every focus loss as a new prompt or invalidate the prompt that caused it. Record background and last meaningful user interaction with a monotonic elapsed-time source. On return, compare elapsed time rather than relying on a timer firing while suspended. If the selected inactivity threshold has expired, or the elapsed time is unavailable or uncertain, remain locked. Use a conservative configurable threshold, with its default subject to product and security review. Start locked after process death because Flutter does not guarantee every lifecycle notification. See [Flutter lifecycle states](https://api.flutter.dev/flutter/dart-ui/AppLifecycleState.html).

Remove the privacy cover only after the app is active and its lock state permits display. Consider native Android window protection for screenshots and app-switcher snapshots; a Flutter overlay alone may not render before the operating system captures a snapshot. Verify the behavior with the actual host. Coordinate external browser sign-in and the system prompt with lifecycle transitions, without granting an unlock just because either returned.

## Browser and embedded WebView

Flutter's `local_auth` package does not list web support. A browser page cannot invoke the native plugin or assume that a device biometric prompt is available. A web UI cover is a privacy convenience, not a secure local lock for stored secrets. Where no verified server-backed WebAuthn flow exists, sign out or require online account sign-in for protected access after the policy expires. Do not invent a client-only PIN or treat a local boolean as authentication. If offline protection of a stored TOTP secret is required on web, treat it as unsupported until a separate, reviewed design provides the required protection.

For a supported browser, a future [WebAuthn](https://developer.mozilla.org/en-US/docs/Web/API/Web_Authentication_API) flow requires a secure context, an appropriate relying-party ID and origin, a registered credential, and browser and authenticator support. Feature detection is not proof that an assertion will succeed. Request user verification when required; it may use a device credential rather than biometrics. The server must issue a fresh, unpredictable, short-lived, single-use challenge and validate registration and assertions, including challenge, expected origin and relying-party ID, credential ownership, signature, and required user presence and verification flags. Only then may the server issue or reauthorize a session. A client-generated challenge or locally checked prompt is not a substitute. WebAuthn reauthentication requires connectivity to that server and does not itself encrypt an offline TOTP secret.

An embedded WebView is not automatically equivalent to a browser or a native Flutter app. The owner of the embedding host must establish its capabilities and origin. Android's [WebView Credential Manager guidance](https://developer.android.com/identity/sign-in/credential-manager-webview) requires host-side integration, feature checks, dependencies, and a Digital Asset Links association for the app and website. Its documented WebKit integration does not support conditional mediation. A different host or version may lack support entirely. If integration or verification is unavailable, use an external trusted browser for online sign-in where the host permits it, or show an unsupported state. Returning from a browser alone must not unlock the app; require a verified, account-bound authentication result. The existing Google sign-in button also expects an external browser, not an embedded provider page.

A native host could instead expose a narrowly scoped local-authentication bridge to trusted content. That requires explicit host implementation, strict origin and navigation checks, request correlation, and lifecycle handling. Never expose a generic success callback to arbitrary pages. Such a bridge is still local UI protection, not server-verifiable authentication. No such bridge is established by the inspected Flutter Android host.

## Secrets, sessions, and revocation

When locked, stop displaying codes and account data, clear transient sensitive view state and in-memory references where practical, and prevent new sensitive actions. Guard asynchronous responses so work started before lock or account change cannot reveal content afterward. Dart cannot guarantee zeroization of immutable strings or copies. Avoid secrets in logs, analytics, clipboard, notifications, screenshots, and crash reports. A lock does not erase already copied data or stop already dispatched requests.

Keep stored tokens and offline secrets out of ordinary preferences and web storage used as if it were a secure enclave. Review the actual platform implementation and backup configuration of secure storage. Gate token restoration, cache reads, and offline profile access behind the lock, while recognizing that a UI gate alone does not cryptographically bind stored values to user authentication. On logout or account switch, invalidate pending work, clear the Dio authorization header and account-scoped local session and cache, and delete the offline profile according to an explicit re-enrollment policy. Local deletion is not remote revocation. Handle deletion failures without displaying old account data to the next user.

Server session expiry and revocation are independent of local lock and unlock. Revalidate online before protected operations and handle unauthorized responses by returning to sign-in. On network failure, do not interpret a retained token or cached wallet snapshot as proof of a valid session or current balance. Offline code generation can continue only under an explicit offline policy and a locally valid profile. Remote device or grant revocation cannot reach a disconnected client, although the online redemption service must enforce current revocation and grant rules. Signing out locally does not guarantee remote logout; remote session and device revocation need supported server operations and clear user feedback.

## Implementation gaps and verification

The native design requires a new dependency, Android host and theme changes, a lock controller, protected data access, and a reviewed recovery policy. Browser WebAuthn requires registration and verification endpoints, credential management, deployment origin decisions, and an online challenge. Embedded WebView support additionally depends on the actual host and its association with the website. These are proposals, not implemented features.

Before release, verify on real supported Android devices with biometrics enrolled, device credential only, no screen lock, cancellation, lockout, and changed enrollment. Exercise process death, prompt interruptions, background and resume, inactivity, external sign-in, logout, account switch, late responses, and app-switcher snapshots. Verify offline code and cache behavior separately from online session expiry and revocation. For web and any WebView, test supported and unsupported hosts, origins, server challenge replay, and fallback flows. This document does not report those tests as completed.
