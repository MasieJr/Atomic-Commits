Offline authorization · connected settlement

Pay whenever, even offline.

Atomic Commits lets a payer generate a short-lived payment code without a live connection. A participating merchant submits that code, the amount and their wallet address; Atomic Commits verifies it and settles through Open Payments using permission the payer approved during onboarding.

What that permission means

The payer does not approve every shop or every purchase.

Setup

Atomic Commits requests an interactive outgoing-payment grant. The payer is redirected to their provider and approves a spending limit, for example R500 per month.

After consent

Atomic Commits receives an access token tied to that grant. While the grant is valid and within its limit, later outgoing payments do not need another payer approval screen.

At redemption

The shop is chosen later. Its wallet address is supplied when the merchant redeems a valid offline code.

Two layers of limits

The wallet grant and the offline code are not the same thing.

Open Payments

Example: Atomic Commits may initiate up to R500 in outgoing payments during the monthly interval.

Atomic Commits

Example: each offline authorization is capped at R50, expires after at most 30 minutes and may only be redeemed once.

Reason

The payer can approve the broad wallet permission once while our app applies tighter rules to every offline purchase.

One setup, many merchants

No payer↔shop pairing.

01

Payer registers with Atomic Commits

The payer device and Atomic Commits server establish the shared secret used to verify future offline codes.

02

The payer ID selects the right secret

When a merchant submits 7K3M 482193, the server uses 7K3M to locate the payer's verification record.

03

The merchant supplies the recipient wallet

The payer did not need to know or pair with that shop in advance. The shop supplies its wallet at redemption.

04

Atomic Commits verifies before payment

The server checks authenticity, time validity, replay state and transaction limits, then executes the payment using the existing grant.

Implementation notes

How the short code works.

The payer ID tells the server which secret to use. The six-digit value proves the payer device knows that secret for a recent 5-minute time window.

Generated locally

No server request is required to create a code after setup.

timeWindow = floor(now / 5 minutes) code = truncate6( HMAC(sharedSecret, payerId + timeWindow) ) display → 7K3M 482193
PAYER IDSelects the payer record and stored verification secret.
6 DIGITSEasy to type or dictate; protected by expiry, rate limits and transaction caps.
SECRETNever sent to the merchant.

Up to 30 minutes

The phone derives a fresh value every five minutes. The server can accept a bounded set of recent windows.

ROTATEFresh code every 5 minutes on the payer device.
VERIFYFor a 30-minute maximum, check the current window and previous five.
CLAIMWhen a code passes verification, record it as used before attempting the payment.
REPLAYAny later attempt with the same payer ID + code is rejected.
The demo rotates every 15 seconds only so the behavior is visible while presenting.
